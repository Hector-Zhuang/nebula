title: 技术路线

---

本文总结 Nebula 当前比较明确的技术路线方向。它用于帮助宿主开发者和平台团队理解 Nebula 的演进重点，而不是作为功能发布日期或交付承诺。

当前我们重点关注的，不是简单增加更多 API 或页面能力，而是继续完善 Nebula 作为小程序运行平台的**安全性、治理能力、可运维性和可扩展性**。

<Info title="欢迎反馈">
  如果你在使用 Nebula 的过程中，对这些技术方向有具体需求、不同判断或新的想法，欢迎持续提出意见与建议。

Nebula 的很多能力边界都与真实业务场景、宿主治理方式和团队协作模式密切相关，来自开发者的一线反馈会直接影响后续设计取舍。

</Info>

## 方向一：JavaScript 沙箱机制

Nebula 未来计划引入更严格的 JavaScript 沙箱机制，用于限制小程序直接访问宿主 React Native 运行时中的任意原生模块。

这项能力的目标包括：

- 限制小程序绕过 Host API 体系直接访问原生模块
- 降低第三方 npm 包直接调用未授权原生能力的风险
- 让宿主能力暴露面更清晰、更可审计
- 为多租户、受监管和高合规场景提供更强的运行时隔离

这项能力会直接影响 Nebula 的平台边界：  
小程序应当通过 Nebula 提供的公开 API 与宿主交互，而不是把宿主运行时视为一个可自由访问的 React Native 环境。

## 方向二：MCP 服务器

Nebula 未来计划提供 MCP 服务器能力，以便让模型、自动化工具和开发工作流更容易理解当前宿主、小程序和 API 的运行上下文。

这项能力可能包括：

- 暴露小程序元数据、页面结构与配置
- 暴露已注册的 Host API 信息
- 暴露组件、能力与版本兼容关系
- 为开发工具、诊断工具和自动化流程提供统一入口

这会让 Nebula 更容易接入：

- AI 辅助开发
- 自动化检查
- 宿主能力发现
- 跨团队协作工具链

## 方向三：文档自动化

Nebula 未来会继续推进文档自动化能力，减少 API、组件和宿主能力在代码与文档之间漂移的问题。

重点方向包括：

- 从 API 定义中提取结构化描述
- 自动生成或校验 reference 文档
- 自动发现缺失的示例、字段说明或兼容性描述
- 将 Host API、组件库和平台能力统一为可消费的文档数据源

这也是为什么在部分能力定义中，会预留如 `description` 这类元数据字段。  
这些字段不仅服务于人工阅读，也服务于后续自动化文档、能力发现和工具链集成。

## 方向四：品牌化

Nebula 未来会逐步增强品牌化能力，以支持不同团队构建更贴近自身产品风格的宿主体验与开发体验。

这类能力可能包括：

- Dev Runner 的品牌化界面与启动体验
- 宿主容器、加载页、错误页和空状态的品牌化
- 小程序目录、入口、分发页面和运营页的品牌化配置
- 与宿主设计系统更一致的运行时视觉能力

这项能力的重点不是单纯“换皮肤”，而是让不同业务宿主能够在统一技术底座上保留自身产品识别度。

## 方向五：Host 对小程序 API 的 Guard

Nebula 未来会加强 Host 对小程序 API 的 guard 机制，让宿主可以更细粒度地决定：

- 哪些 API 可以暴露
- 哪些 API 只能在特定宿主版本中暴露
- 哪些 API 需要额外权限或上下文校验
- 哪些 API 在某些租户、用户或场景下应被禁止

这类 guard 机制可能覆盖：

- 能力注册阶段的静态控制
- 运行时的参数校验与调用拦截
- 权限与身份上下文绑定
- 更明确的错误返回与审计记录

这项能力会和 JavaScript 沙箱、Host API 系统以及合规治理共同组成更完整的平台保护层。

## 总结

Nebula 接下来的技术路线，核心不是把它做成一个“更自由的动态代码分发系统”，而是把它演进为一个**更可控、更安全、更可治理的小程序平台**。

从这个目标出发，未来的重点会集中在：

- 更强的运行时隔离
- 更明确的宿主能力边界
- 更好的自动化与工具链接入
- 更完整的品牌化能力
- 更严格的 API 守卫与治理机制

如果你正在基于 Nebula 规划宿主平台、合规治理或内部小程序体系，这些方向会比单纯增加若干业务 API 更值得优先关注。
