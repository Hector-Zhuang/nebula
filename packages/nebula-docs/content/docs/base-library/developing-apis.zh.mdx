title: 开发新 API
description: 将新的 Nebula API 设计为稳定的平台能力，而不是宿主内部实现的直接暴露。
---

新的 Nebula API 应该被设计成 **平台能力**。

这意味着：即使宿主侧实现会随时间变化，小程序开发者感受到的 API 也应保持稳定。一个好的 Nebula API，不只是“宿主能做的一件事”，而应该是一项具有以下特征的能力：

- 清晰的所有权边界
- 稳定的请求与结果结构
- 可预期的平台行为
- 能支持兼容性检查与未来演进

## 先问一个问题

在新增 API 之前，先问：

> 这项能力属于 Nebula 平台本身，还是只属于某个业务宿主？

如果它只和单一宿主或单一业务流程相关，通常就 **不应该** 进入基础库。

适合成为 Nebula 平台能力的例子包括：

- 扫码
- 定位
- 媒体选择
- 剪贴板
- 文件传输
- 系统信息

不适合的例子包括：

- 结账相关操作
- 租户专属数据查询
- 产品专属工作流捷径
- 任何直接暴露宿主内部服务的能力

## 选择正确的层

大多数新能力都会同时触及多个包。设计时最关键的问题，是每一部分该放在哪一层。

| 层 | 责任 |
|---|---|
| `@nebula-rn/client` | 面向小程序开发者的稳定 API 表面 |
| `@nebula-rn/sdk` | 运行时协议、宿主调用原语、共享类型 |
| `@nebula-rn/host-apis` | 官方宿主侧能力实现 |
| Host app | 业务专属行为或自定义扩展 |

通常可以这样判断：

- **小程序侧直接调用的函数** 放在 `@nebula-rn/client`
- **协议和低层原语** 留在 `@nebula-rn/sdk`
- **官方可复用的宿主实现** 放在 `@nebula-rn/host-apis`
- **业务专属变体** 留在宿主工程里，而不是基础库

## 选择能力形态

Nebula 的宿主能力通常分成两类。

### 非视觉 API

当宿主只需要执行逻辑并返回结果时，使用 `createHostApiFeature(...)`。

例如：

- `getLocation`
- `getBatteryInfo`
- `getClipboardData`

适用场景：

- 不需要宿主管理的界面
- 请求可以在一次逻辑调用中完成
- 结果可以直接返回

### Modal API

当宿主必须先展示一段宿主侧交互流程，用户完成交互后再返回结果时，使用 `createHostModalApiFeature(...)`。

例如：

- `scanCode`
- 图片预览
- 权限确认流程

适用场景：

- 宿主需要渲染自己的 UI
- 能力依赖宿主管理的 modal 或 overlay
- 结果要等用户操作完成后才能确定

## 推荐的设计流程

### 1. 先定义小程序侧契约

先从小程序开发者最终会用到的 API 形状开始设计。

重点考虑：

- 函数名
- 输入参数
- 返回结果
- 错误模型
- 超时预期

这个契约应当在不了解宿主内部实现的前提下也能被理解。

### 2. 判断它是标准能力还是宿主私有能力

如果这项能力希望被多个宿主复用，它可能属于：

- `@nebula-rn/client`
- `@nebula-rn/host-apis`

如果它是业务专属能力，则更适合：

- 放在宿主自有能力实现中
- 在宿主工程里维护配套文档

不要因为多个页面都用到了某个能力，就把它直接提升到基础库。

### 3. 围绕能力边界来设计

一个新的 API 应该让能力边界更清晰，而不是更模糊。

可以这样检查：

- 宿主是否明确选择开放这项能力？
- 小程序是否能判断它是否可用？
- 平台差异是否被足够好地隐藏起来？
- 宿主是否可以安全地拒绝请求？

如果这些问题的答案都不明确，那么 API 契约通常还是太贴近宿主内部实现。

### 4. 实现宿主能力

宿主侧能力应该放在：

- `@nebula-rn/host-apis`：官方可复用实现
- 宿主工程：业务专属实现

然后通过下面的方式注册：

```tsx
NebulaAPI.wrap({
  hostApis: [...],
})(App);
```

### 5. 验证完整结果路径

不要在宿主侧代码能编译通过之后就停止。

要验证完整链路：

- 小程序发起调用
- 宿主收到请求
- 宿主完成逻辑或 modal 交互
- 结果以预期结构返回
- 失败场景对调用方仍然清晰可理解

## 设计建议

### 用能力语言，而不是实现语言

更好的命名：

- `scanCode`
- `getLocation`
- `chooseMedia`

不够好的命名：

- `openNativeCameraScanner`
- `fetchHostUserContext`
- `invokeSystemXYZ`

API 名称应该描述“能力”，而不是宿主内部怎么做。

### 保持结果结构稳定

宿主实现可以演进，但小程序开发者看到的结果结构应该尽量稳定。

例如，如果一个标准化结构已经足够，就不要直接暴露原生侧的零散返回值。

### 避免泄露宿主 UI 假设

小程序开发者不应该需要知道：

- 宿主实际渲染了哪个组件
- 使用了哪个原生控制器
- 宿主如何组织内部交互流程

这些都属于宿主侧实现细节。

### 不要让消息通信代替正式 API

如果一项能力会被反复使用，它通常应该演化成结构化 Host API，而不是长期依赖临时消息协议。

## 以 `scanCode` 作为参考形态

`scanCode` 是一个很好的参考，因为它同时体现了：

- `@nebula-rn/client` 中稳定的小程序调用函数
- 宿主管理的 modal 交互
- 官方可复用的宿主实现
- 从宿主返回到小程序的清晰结果路径

它是一个很好的参考形状，但不应该被当成所有 API 的模板。有些能力本身就更简单，完全可以保持为非视觉 API。
