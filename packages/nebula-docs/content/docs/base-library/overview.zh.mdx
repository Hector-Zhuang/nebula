Nebula 基础库是 **面向平台的能力层**，由小程序和宿主共同依赖。

它要回答的核心问题只有一个：

> 哪些能力应该让小程序开发者感受到稳定，即使宿主实现会随着时间演进？

因此，这一组文档关注的不是业务 API，而是 Nebula 平台本身对外暴露的能力模型。

## 这里包含什么

基础库关注“平台能力如何被建模、暴露和实现”的可复用层：

| 包 | 角色 |
|---|---|
| `@nebula-rn/client` | 面向小程序开发者的稳定 API 表面 |
| `@nebula-rn/sdk` | 运行时协议、宿主调用原语、共享类型 |
| `@nebula-rn/host-apis` | 官方宿主侧能力实现集合 |

这些层共同让 Nebula 提供的 API 同时具备以下特征：

- 小程序开发者容易理解
- 宿主显式注册后才可用
- 能配合能力探测与版本兼容
- 能扩展，但不泄露宿主内部实现

## 什么不应该放在这里

基础库不应该成为产品逻辑或宿主私有逻辑的容器。

以下能力通常 **不应** 放进基础库：

- 结账或电商流程
- 租户专属查询
- 应用专属业务上下文
- 私有宿主服务
- 一次性集成捷径

这类能力即使会暴露给小程序，也更适合留在宿主工程里，通过自定义 Host API 提供。

## 设计目标

Nebula 基础库里的能力，通常应追求四个目标。

### 稳定的小程序契约

小程序开发者接触到的能力名、输入参数和返回结果，应该尽量长期稳定。

### 清晰的宿主所有权

基础库定义的是能力模型，不是强制行为。真正决定某项能力是否开放给小程序的，仍然是宿主。

### 兼容性感知的演进

能力演进应当能配合版本检查、能力探测和优雅降级一起工作。

### 与宿主内部解耦

Nebula API 应该描述“能力”，而不是宿主内部某个具体实现细节。

## 常见能力类别

比较适合放进基础库的平台能力通常包括：

- 扫码
- 媒体选择
- 设备信息
- 定位
- 网络
- 存储
- 文件传输
- 剪贴板

它们适合作为基础库能力，是因为不同宿主都能把它们收敛成一套共享契约。

## 心智模型

可以把基础库理解成三层协作：

1. `@nebula-rn/client` 定义小程序开发者调用什么
2. `@nebula-rn/sdk` 定义运行时如何传输和组织这项能力
3. `@nebula-rn/host-apis` 定义宿主如何以可复用方式实现这项能力

正是这层拆分，让 Nebula 能保持小程序 API 稳定，同时又不要求所有宿主共享同一套内部实现。

## 一个简单判断标准

如果一项能力在多个宿主里、即使实现不同，也依然有平台级意义，那么它可能属于基础库。

如果它只服务于某个宿主或某条业务流程，那么它通常更适合留在宿主自有 API 中。
