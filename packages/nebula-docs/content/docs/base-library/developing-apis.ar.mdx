يجب تصميم واجهات Nebula الجديدة على أنها **قدرات منصة**.

أي أن API يجب أن يبدو مستقراً لمطور التطبيق المصغّر، حتى لو تغيّر التنفيذ على جانب المضيف بمرور الوقت. واجهة Nebula الجيدة ليست مجرد "شيء يمكن للمضيف فعله"، بل هي قدرة ذات:

- حدود ملكية واضحة
- بنية طلب ونتيجة مستقرة
- سلوك منصة متوقع
- قابلية لفحوص التوافق والتطور لاحقًا

## ابدأ بسؤال واحد

قبل إضافة API جديد، اسأل:

> هل تنتمي هذه القدرة إلى منصة Nebula نفسها، أم أنها مجرد سلوك خاص بمضيف أو منتج واحد؟

إذا كانت مرتبطة فقط بمضيف واحد أو بتدفق أعمال محدد، فعادة **لا ينبغي** أن تصبح جزءًا من المكتبة الأساسية.

أمثلة على قدرات مناسبة كقدرات منصة:

- المسح
- الموقع
- اختيار الوسائط
- الحافظة
- نقل الملفات
- معلومات النظام

أمثلة غير مناسبة:

- عمليات مرتبطة بالدفع
- استعلامات بيانات خاصة بمستأجر معيّن
- اختصارات خاصة بتدفق منتج محدد
- أي شيء يكشف خدمات المضيف الداخلية مباشرة

## اختر الطبقة المناسبة

غالبية القدرات الجديدة تلامس أكثر من حزمة. القرار الأساسي هو: أين تنتمي كل طبقة؟

| الطبقة | المسؤولية |
|---|---|
| `@nebula-rn/client` | سطح API مستقر موجّه للتطبيقات المصغّرة |
| `@nebula-rn/sdk` | بروتوكول وقت التشغيل، وأدوات الاستدعاء، والأنواع المشتركة |
| `@nebula-rn/host-apis` | التنفيذات الرسمية للقدرات على جانب المضيف |
| تطبيق المضيف | سلوك خاص بالأعمال أو توسعات مخصصة |

القاعدة العامة:

- ضع **الدالة التي يستدعيها التطبيق المصغّر** في `@nebula-rn/client`
- أبقِ **البروتوكول والأدوات منخفضة المستوى** في `@nebula-rn/sdk`
- ضع **التنفيذ الرسمي القابل لإعادة الاستخدام** في `@nebula-rn/host-apis`
- أبقِ **النسخ الخاصة بالأعمال** داخل تطبيق المضيف، لا في المكتبة الأساسية

## اختر شكل القدرة

عادةً ما تقع قدرات Nebula على جانب المضيف ضمن شكلين رئيسيين.

### API غير مرئي

استخدم `createHostApiFeature(...)` عندما يحتاج المضيف فقط إلى تنفيذ منطق ثم إعادة نتيجة.

مثل:

- `getLocation`
- `getBatteryInfo`
- `getClipboardData`

وهذا الشكل مناسب عندما:

- لا توجد حاجة إلى واجهة يديرها المضيف
- يمكن إكمال الطلب في خطوة منطقية واحدة
- يمكن إعادة النتيجة مباشرة

### Modal API

استخدم `createHostModalApiFeature(...)` عندما يحتاج المضيف إلى عرض تدفق تفاعلي مملوك له قبل إعادة النتيجة.

مثل:

- `scanCode`
- معاينة الصور
- تدفقات تأكيد الأذونات

وهذا الشكل مناسب عندما:

- يحتاج المضيف إلى عرض واجهته الخاصة
- تكون القدرة مدفوعة بنافذة modal أو overlay يديرها المضيف
- لا تُعرف النتيجة إلا بعد انتهاء تفاعل المستخدم

## سير عمل مقترح للتصميم

### 1. عرّف العقد الموجّه للتطبيق المصغّر

ابدأ بشكل API الذي سيستخدمه مطور التطبيق المصغّر فعليًا.

ركّز على:

- اسم الدالة
- خيارات الإدخال
- شكل النتيجة
- نموذج الأخطاء
- توقعات المهلة

يجب أن يكون هذا العقد قابلاً للفهم دون معرفة تنفيذ المضيف.

### 2. حدّد إن كانت القدرة قياسية أم خاصة بالمضيف

إذا كانت القدرة مخصصة لإعادة الاستخدام عبر أكثر من مضيف، فقد تنتمي إلى:

- `@nebula-rn/client`
- `@nebula-rn/host-apis`

أما إذا كانت خاصة بالأعمال، فالأفضل أن تبقى:

- ضمن تنفيذ خاص بالمضيف
- مع وثائق مخصصة داخل مشروع المضيف

لا تنقل API إلى المكتبة الأساسية لمجرد أن أكثر من شاشة تستخدمه.

### 3. صمّم مع احترام حدود القدرة

يجب أن تجعل API الجديدة حدود القدرة أوضح، لا أكثر غموضًا.

اسأل:

- هل يختار المضيف صراحةً تفعيل هذه القدرة؟
- هل يمكن للتطبيق المصغّر اكتشاف توفرها؟
- هل تم إخفاء الفروقات بين المنصات بشكل كافٍ؟
- هل يستطيع المضيف رفض الطلب بشكل آمن؟

إذا لم تكن الإجابة واضحة، فغالبًا ما يكون العقد قريبًا أكثر من اللازم من تفاصيل المضيف الداخلية.

### 4. نفّذ القدرة على جانب المضيف

أنشئ التنفيذ في:

- `@nebula-rn/host-apis` للتنفيذات الرسمية القابلة لإعادة الاستخدام
- تطبيق المضيف للتنفيذات الخاصة بالأعمال

ثم قم بالتسجيل عبر:

```tsx
NebulaAPI.wrap({
  hostApis: [...],
})(App);
```

### 5. تحقّق من مسار النتيجة الكامل

لا تتوقف عند مرحلة أن الكود صار قابلاً للترجمة.

تحقق من المسار الكامل:

- التطبيق المصغّر يستدعي API
- المضيف يستقبل الطلب
- المضيف ينفذ المنطق أو يكمل تدفق modal
- النتيجة تعود بالشكل المتوقع
- حالات الفشل تبقى واضحة للمستدعي

## إرشادات تصميم

### فضّل لغة القدرة على لغة التنفيذ

أمثلة جيدة:

- `scanCode`
- `getLocation`
- `chooseMedia`

أمثلة أقل جودة:

- `openNativeCameraScanner`
- `fetchHostUserContext`
- `invokeSystemXYZ`

يجب أن يصف اسم API القدرة نفسها، لا تفاصيل تنفيذ المضيف.

### حافظ على استقرار أنواع النتائج

قد يتطور تنفيذ المضيف، لكن النتيجة الموجّهة للتطبيق المصغّر يجب أن تبقى مستقرة قدر الإمكان.

ولهذا، لا تكشف حمولة أصلية خام إذا كان شكل موحّد يكفي.

### تجنب كشف افتراضات واجهة المضيف

لا يجب أن يحتاج مطور التطبيق المصغّر إلى معرفة:

- أي مكوّن يعرضه المضيف
- أي متحكم أصلي يستخدمه
- كيف ينظم المضيف تدفقه الداخلي

كل هذه تفاصيل تخص المضيف.

### لا تجعل التراسل غير المنظم بديلاً عن API رسمي

إذا كانت القدرة مهمة بما يكفي للاستخدام المتكرر، فمن الأفضل أن تصبح Host API منظّمة بدلاً من الاعتماد على عقد رسائل مؤقتة.

## `scanCode` كمرجع شكلي

يبقى `scanCode` مثالاً مرجعيًا جيدًا لأنه يوضح:

- دالة مستقرة موجّهة للتطبيق المصغّر داخل `@nebula-rn/client`
- تفاعلًا modal يديره المضيف
- تنفيذًا رسميًا قابلاً لإعادة الاستخدام
- مسار نتيجة واضح يعود إلى التطبيق المصغّر

وهو مفيد كمرجع، لكنه ليس القالب المناسب لكل API. فبعض القدرات أبسط بكثير ويجب أن تظل غير مرئية.
