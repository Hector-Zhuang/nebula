title: 业务场景
description: 了解 Nebula 小程序架构适用的业务场景，以及它相比 WebView 和纯原生方案的优势。

Nebula 适用于需要在一个宿主应用中承载多个独立业务模块的场景。每个模块作为独立小程序开发、部署和更新，无需跟随宿主应用的发版节奏。

## 场景一：超级应用（Super App）

最容易理解的类比就是 **微信式超级应用**：

```
微信（宿主应用）
├── 微信支付          ← 小程序
├── 京东购物          ← 小程序
├── 滴滴出行          ← 小程序
├── 美团外卖          ← 小程序
├── 12306 出行        ← 小程序
└── ...更多服务型小程序
```

**核心诉求：**

- 宿主提供统一的用户入口和基础能力（支付、定位、登录）
- 各业务方独立开发、独立发布，无需等待宿主发版
- 宿主控制权限和能力边界，保障安全性
- 用户无需安装多个 App，在一个应用内完成各类操作

**Nebula 如何满足：**

| 诉求 | Nebula 方案 |
|------|-------------|
| 统一能力接口 | Host API 注册机制，宿主定义并暴露标准 API |
| 独立发布 | Nebula Cloud 版本管理，小程序独立上传/发布 |
| 安全隔离 | 沙箱隔离，小程序之间文件和存储互不可见 |
| 快速加载 | 预加载机制减少冷启动延迟 |

## 场景二：企业级 B 端应用

一个大型企业的内部管理系统，包含多个业务子模块：

```
企业管理平台（宿主应用）
├── 仓储管理          ← 小程序（仓储团队开发）
├── 审计系统          ← 小程序（审计团队开发）
├── 销售 CRM          ← 小程序（销售团队开发）
├── HR 人事           ← 小程序（HR 团队开发）
├── 财务报销          ← 小程序（财务团队开发）
└── 设备巡检          ← 小程序（运维团队开发）
```

**核心诉求：**

- 各团队独立开发各自模块，互不阻塞
- 统一入口，员工使用一个 App 完成所有工作
- 宿主统一提供扫码、拍照、定位、通知推送等硬件能力
- 模块可以按需灰度发布，快速修复线上问题
- 不同模块之间数据隔离，保障业务安全

**Nebula 如何满足：**

| 诉求 | Nebula 方案 |
|------|-------------|
| 团队独立开发 | 每个模块独立仓库、独立构建、独立上传 |
| 统一硬件能力 | 宿主通过 Host API 暴露扫码、拍照等原生能力 |
| 体验与上线分流 | 上传后自动成为体验版，再提交审核并发布上线 |
| 热修复 | 更新策略支持自动检查并应用新版本 |
| 数据隔离 | 每个小程序独立沙箱，文件和存储互不可见 |

## 场景三：AI Chatbot 生成应用

用户通过自然语言对话，让 AI Chatbot 自动生成并部署小程序：

```
用户: "帮我做一个库存盘点应用，支持扫码录入和导出 Excel"

Chatbot:
  1. 生成 React Native 页面代码（扫码、列表、导出）
  2. 调用 nebula miniapp build 构建 bundle
  3. 调用 nebula miniapp upload 上传到 Nebula Cloud
  4. 宿主应用自动发现并加载新小程序

用户打开宿主 App → 库存盘点应用已就绪
```

**核心诉求：**

- Chatbot 生成的代码能够直接打包为可运行的小程序
- 生成→构建→部署全链路自动化，无需人工介入开发环节
- 宿主应用无需重新编译或发版即可加载新生成的小程序
- 生成的应用可以调用原生能力（扫码、拍照、定位等）
- 支持持续迭代——用户对话修改需求，Chatbot 更新小程序

**Nebula 如何满足：**

| 诉求 | Nebula 方案 |
|------|-------------|
| 标准化输出 | 小程序使用 React + TypeScript，对 LLM 代码生成友好 |
| 自动化部署 | CLI 提供 `build` + `upload` 命令，可被 Chatbot 脚本调用 |
| 免发版加载 | 宿主通过 OTA 安装新 bundle，无需 App Store 审核 |
| 原生能力 | Host API 机制暴露扫码、文件系统等能力，生成代码直接调用 |
| 迭代更新 | Nebula Cloud 版本管理，Chatbot 上传新版本即可覆盖 |
| 安全边界 | 沙箱隔离确保 AI 生成的代码不会影响宿主和其他小程序 |

**典型流程：**

```
┌──────────┐     ┌──────────┐     ┌─────────────────┐     ┌──────────┐
│  用户     │────▶│ Chatbot  │────▶│ Nebula Cloud │────▶│ 宿主 App  │
│ (对话)    │     │ (生成代码)│     │ (构建/上传)      │     │ (OTA加载) │
└──────────┘     └──────────┘     └─────────────────┘     └──────────┘
      │                                                         │
      └─────────────── 打开新生成的小程序 ◀─────────────────────┘
```

这个场景的关键在于 Nebula 的**动态加载能力**——宿主是一个通用容器，具体业务逻辑完全由小程序承载。AI 生成的代码只需遵循小程序的开发规范（`createMiniAppPage`、`definePageConfig`、生命周期 hooks），即可被宿主无缝加载和运行。

## 为什么不用 WebView

Nebula 不是浏览器壳：

| 对比项 | WebView | Nebula |
|--------|---------|--------|
| 渲染 | Web 渲染 | React Native 原生渲染 |
| 性能 | 受限于浏览器引擎 | 接近原生性能 |
| 硬件能力 | 需要 JSBridge 逐个桥接 | Host API 统一注册机制 |
| 页面管理 | 单页应用或 iframe | 原生页面栈，支持预加载 |
| 生命周期 | 粗粒度（visibilitychange） | 细粒度（onShow/onHide/onReady 等） |
| 离线能力 | 有限 | Bundle 本地缓存，离线可用 |

## 为什么不全部写在宿主里

将所有业务代码打包进宿主应用会带来以下问题：

- **发版耦合**：任何一个模块的改动都需要整个 App 发版，受应用商店审核周期制约
- **代码膨胀**：所有模块代码打进一个包，安装体积不断膨胀
- **团队阻塞**：多团队在同一仓库协作，合并冲突频繁
- **回滚困难**：无法单独回滚某个模块，只能整体回滚

Nebula 通过小程序架构将业务模块解耦：独立仓库、独立构建、独立发布、独立回滚，宿主只需提供容器和基础能力。
